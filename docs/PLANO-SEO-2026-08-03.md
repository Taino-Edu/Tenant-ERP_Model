### Duas armadilhas do App Router que custaram bug aqui

Metadados **não** mesclam campo a campo entre layout e página: o objeto do
filho substitui o do pai inteiro, e o que o filho não declara é herdado como
está. As duas consequências apareceram em produção neste trabalho:

- **Canônico herdado.** O layout de `/produtos` declara `canonical: '/produtos'`.
  Sem declarar o próprio, cada página de produto herdava esse valor — ou seja,
  dizia ao Google "não me indexe, indexe a listagem". Todo o catálogo sairia da
  busca. Hoje `/produtos/[id]` declara o canônico nos dois caminhos de retorno.
- **`og:image` apagado.** Bastava uma página declarar `openGraph` com um título
  próprio para perder a imagem definida no layout raiz — e o sintoma não é erro
  nenhum, é o link colado no WhatsApp aparecer sem foto. Toda página que declara
  `openGraph` chama `resolveShareImage()`.

### Fora do índice, de propósito

`/perfil/[id]` e `/mesa/[mesa]` ganharam `noindex` **e** entrada no `robots.txt`.
Os dois porque fazem coisas diferentes: o `robots` impede o rastreio novo, a
meta tag tira do índice o que já entrou. Só o `robots` não desindexa — o Google
mantém a URL listada quando não consegue rastrear para ver a meta tag.

`/perfil/[id]` é o caso que mais importa: mostra nome, foto, tempo de casa,
número de compras e saldo de pontos de uma pessoa física. Acessível por link é
uma coisa; pesquisável pelo nome no Google é outra.

Sobre o item 2: o canônico ficou absoluto em `/privacidade`, `/termos` e
`/cookies`, que são o mesmo texto servido em todo host onde o app responde —
uma cópia por loja, competindo entre si. Para a vitrine de cada tenant o
canônico continua sendo o padrão do Next (o próprio host), que é o certo: o
conteúdo daquela loja é dela.

O passo a passo do Search Console e do PageSpeed está em
[GOOGLE-SEARCH-CONSOLE.md](GOOGLE-SEARCH-CONSOLE.md).

## Pendente — itens do diagnóstico original de SEO

### 1. `robots.txt` e `sitemap.xml` por tenant
**Por quê:** sem sitemap, buscadores não têm como descobrir todas as páginas
de produto de cada loja. Sem robots.txt, rotas administrativas (`/admin`,
`/plataforma`, `/contador`) podem ser rastreadas à toa.
**Onde mexer:** `app/robots.ts` e `app/sitemap.ts` (arquivos especiais do
Next.js App Router, mesmo mecanismo de `app/manifest.ts` já existente).
Sitemap precisa ser dinâmico por tenant (via `headers()` + slug, mesmo padrão
de `lib/serverSiteConfig.ts`/`lib/serverProduct.ts`) — listar produtos com
`ShowOnSite=true` de cada loja. Vai precisar de um endpoint público novo tipo
`GET /api/public/sitemap?slug=...` devolvendo ids/updatedAt de produtos ativos.
**Esforço:** médio (endpoint novo + os dois arquivos especiais do Next).

### 2. Canonical tags
**Por quê:** multi-tenant serve por subdomínio + domínio próprio (BYO domain)
+ possivelmente `www` — sem canonical, risco real de conteúdo duplicado entre
variantes de host pro mesmo tenant.
**Onde mexer:** `alternates.canonical` no `generateMetadata` de `app/layout.tsx`
e `app/produtos/[id]/page.tsx` (usar o host resolvido + path atual).
**Esforço:** baixo.

### 3. `<h1>` faltando em `/produtos` (listagem)
**Por quê:** página de descoberta de produtos sem heading principal — só tem
`<h2>` por categoria.
**Onde mexer:** `app/produtos/page.tsx`.
**Esforço:** baixo (é só adicionar o elemento, layout já existe).

### 4. `next/image` no lugar de `<img>` cru
**Por quê:** imagens de produto/logo usam `<img>` com
`eslint-disable @next/next/no-img-element` — perde otimização automática
(lazy-load, responsivo, WebP/AVIF), afeta LCP (Core Web Vitals).
**Onde mexer:** `app/page.tsx`, `app/produtos/page.tsx`,
`app/produtos/[id]/ProdutoDetalheClient.tsx`, `app/perfil/[id]/page.tsx`,
`app/mesa/[mesa]/page.tsx` — todo lugar com o disable comment.
**Esforço:** médio (precisa checar `next.config.js` `images.remotePatterns`
pra cada domínio de imagem já usado, e ajustar layout já que `next/image`
exige `width`/`height` ou `fill`).

### 5. gzip no nginx
**Por quê:** `nginx.conf` não tem `gzip` habilitado — pode pesar no tempo de
carregamento.
**Onde mexer:** `deploy/nginx/nginx.conf` (bloco `http`/`server`).
**Verificar antes:** se os domínios próprios (BYO domain) já passam pelo
Cloudflare, ele pode já comprimir na frente — nesse caso o ganho real é só
pro acesso direto ao domínio da plataforma.
**Esforço:** baixo.

## Ordem sugerida
1. Canonical tags (rápido, resolve um risco real de duplicação)
2. `<h1>` em `/produtos` (rápido)
3. gzip no nginx (rápido, mas confirmar o papel do Cloudflare antes)
4. robots.txt + sitemap.xml (médio, mais valor de descoberta orgânica)
5. `next/image` (médio/maior, mexe em mais arquivos — deixar por último)
